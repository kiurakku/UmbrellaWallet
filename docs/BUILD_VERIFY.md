# Build & Verify Umbrella Wallet

*Don't trust — verify.* This wallet is open source and keyless. You never have to take our word
that the binary you run matches the source you can read. This guide shows you how to (a) check a
downloaded release against its published hash, and (b) build the exact same app yourself from source.

> The strongest guarantee is **b) build it yourself.** A matching hash proves the file wasn't
> altered in transit; a self-built binary proves the code is the code.

---

## A. Verify a downloaded release (30 seconds)

Every GitHub release ships a `SHA256SUMS.txt` covering every artifact (installer, portable zip, Linux
tarball). It's generated by CI *after* all platform builds finish, and CI fails the release if the
artifact set is incomplete or if any line doesn't match its file — so the manifest is always complete
and self-consistent. Compute the hash of what you downloaded and compare.

**Windows (PowerShell):**

```powershell
Get-FileHash .\UmbrellaWallet-Setup-4.5.0.exe -Algorithm SHA256
```

**Linux / macOS:**

```bash
sha256sum UmbrellaWallet-Setup-4.5.0.exe
```

The printed hash must match the line in `SHA256SUMS.txt` **exactly** (case-insensitive). For the
4.5.0 installer that is:

```
67768E35D89F4AEADEB699E90EB402B8A86583DDC9041437767972AF3D46E7D9  UmbrellaWallet-Setup-4.5.0.exe
```

If it doesn't match, **stop** — do not run it. Re-download from the official release page and, if it
still differs, report it. (The `SHA256SUMS` file itself is only as trustworthy as the channel you got
it from; that's why building from source, below, is the real proof.)

## B. Build it yourself

### Toolchain (pin these)

| Component | Version used for the official 4.5.0 build |
|---|---|
| .NET SDK | **8.0.423** (`dotnet --version`) |
| Target framework | `net8.0`, runtime `win-x64`, self-contained |
| Inno Setup | 6.x (`ISCC.exe`) — only needed to rebuild the installer |

Any 8.0.4xx SDK produces the same **managed** assemblies (the compiler is deterministic — see caveats).
Pin 8.0.423 if you want to reproduce the native `apphost`/installer as closely as the platform allows.

### Steps

```bash
git clone <repo-url> umbrella-wallet
cd umbrella-wallet
git checkout v4.5.0            # build the exact released tag, not the moving branch

dotnet test                   # optional but recommended — crypto is pinned to published test vectors
```

Then run the one-shot release script (it stages the bundled Tor + Monero binaries, publishes, and
builds the installer):

```powershell
pwsh desktop/scripts/release-windows.ps1
```

Or reproduce the publish by hand — this is exactly what the script and CI run:

```powershell
$csproj = "desktop/src/Umbrella.Wallet.App/Umbrella.Wallet.App.csproj"

# Folder publish (what the installer packages)
dotnet publish $csproj -c Release -r win-x64 --self-contained true `
  -p:PublishSingleFile=false -o dist/app

# Portable single-file build
dotnet publish $csproj -c Release -r win-x64 --self-contained true `
  -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -o dist/portable
```

The apphost is then renamed `Umbrella.Wallet.App.exe → Umbrella.exe` (the managed assembly keeps its
name so `avares://` resource URIs still resolve; the apphost loads its dll by the *embedded* name, so
renaming only the exe is safe).

## C. What is and isn't reproducible (the honest part)

.NET makes the **C# compilation deterministic** but a self-contained, single-file publish is **not
bit-for-bit reproducible** across arbitrary machines. Be precise about what each layer guarantees:

| Layer | Reproducible? | Why |
|---|---|---|
| Managed assemblies (`Umbrella.Wallet.*.dll`) | ✅ **Yes** — deterministic | Roslyn defaults to `Deterministic=true`. Verified on this toolchain: two clean rebuilds of `Umbrella.Wallet.Core.dll` produced the **byte-identical** hash `5C61E3A7B093…D307`. Same source + same SDK ⇒ same DLL, on any machine. No build-machine path leaks into the output (the shipped DLLs/PDBs contain no source path). |
| Bundled runtime (`coreclr`, `System.*` from the shared framework) | ✅ if the SDK version matches | These are the .NET runtime's own signed binaries, copied verbatim. |
| Native `apphost` (`Umbrella.exe`) | ⚠️ Mostly | The apphost is patched with the app name at publish; a differing SDK **patch** version can change it. |
| Single-file bundle / installer `.exe` | ❌ Not bit-identical | The bundler embeds timestamps and compresses; Inno Setup embeds a build time. Hashes will differ between two machines even with identical inputs. |

**So how do you verify without a matching installer hash?** Compare the part that carries the logic —
the **managed assemblies** (`Umbrella.Wallet.Core/Infrastructure/App.dll`). These are what derive your
keys, sign your transactions, and route traffic through Tor. Because the build is deterministic, they
are byte-identical for anyone who builds the **same commit** with the **same SDK**:

```powershell
# 1. build the exact released commit, 2. hash the managed DLLs
git checkout v4.5.0
dotnet publish desktop/src/Umbrella.Wallet.App/Umbrella.Wallet.App.csproj `
  -c Release -r win-x64 --self-contained true -p:PublishSingleFile=false -o dist/app
Get-ChildItem dist/app/Umbrella.Wallet.*.dll |
  ForEach-Object { "{0}  {1}" -f (Get-FileHash $_ -Algorithm SHA256).Hash, $_.Name }
```

Then extract the same three DLLs from a downloaded release and hash them. Matching hashes prove the
wallet's behaviour is the source you read — regardless of installer packaging noise.

> **Important caveat for 4.5.0:** this build was produced from the active release branch, not a clean
> tagged commit, so there is not yet a published set of managed-DLL hashes to diff against. Determinism
> is proven (above), but turnkey DLL verification lands once releases are cut from an immutable tag with
> a `global.json`-pinned SDK and a published `SHA256SUMS-managed-<version>.txt` — see below.

### Toward stricter reproducibility (roadmap)

- Publish a `SHA256SUMS` of the **managed assemblies** alongside the installer hash, so a self-build
  can be diffed without unpacking the installer.
- Add `ContinuousIntegrationBuild=true` + `SourceLink` in CI so PDB paths are normalised to repo-
  relative and traceable to the exact commit.
- Pin the SDK with a `global.json` so `dotnet` refuses to build with a drifting patch version.

## D. Prove privacy at runtime

Building honestly is half of "verify"; the other half is confirming the running app behaves. Inside
the wallet:

- **Settings → Verify Tor** — proves your traffic actually exits through a Tor node, not clearnet.
- **Tor-only kill-switch** is fail-closed: with it on, any attempt to reach a non-proxied endpoint is
  refused, never silently downgraded to clearnet.
- No telemetry, no crash reporting, no analytics, no accounts, no API keys — see
  [`SECURE_ANON_ROADMAP.md`](SECURE_ANON_ROADMAP.md) for the full security posture and its status.
